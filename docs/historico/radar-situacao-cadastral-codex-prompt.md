## Desenho proposto
1. carga.ts: no início, baixa da edge a lista de CNPJs conhecidos (ação nova `cnpjs_conhecidos`, paginada por keyset `apos`/`limite` ≤ 50.000, RPC `radar_cnpjs_conhecidos(p_apos,p_limite) RETURNS text[]` = radar_empresas.cnpj ∪ radar_docs_clientes()). No loop por zip, UMA leitura do CSV vira temp table `scan` com `WHERE (situacao='02' AND cnae1 IN alvo) OR (b||o||dv IN conhecidos)`; dela saem 2 parquets: o filtrado atual (inalterado) e `sit_conhecidos_i` (cnpj, situacao, dt_sit, motivo, cnae1). Cache/resume: pula o zip só se os DOIS parquets existem. Depois dos chunks normais, POST `chunk_situacao` (1000/vez) com {cnpj, situacao, data_situacao, motivo_codigo, motivo_descricao}; CNPJ validado por montarCnpj (DV); linha fora do formato é contada por motivo. Dry-run sem edge: `--conhecidos <csv>` opcional, senão pula a extração com aviso.
2. Banco (migration única, idempotente, BEGIN/COMMIT + DO $post$):
   - `radar_situacao_cadastral(cnpj text CHECK formato, lote text CHECK 'YYYY-MM', situacao text CHECK IN ('01','02','03','04','08'), data_situacao date, motivo_codigo text, motivo_descricao text, observado_em timestamptz NOT NULL default now(), alertado_em timestamptz, PK (cnpj, lote))`. SEM FK para radar_empresas (cliente fora do radar também entra). RLS: SELECT para authenticated via pode_ver_carteira_completa(auth.uid()) como as demais radar_*; escrita só service_role (bypass). Índice (lote, situacao).
   - `radar_empresas` ganha 3 colunas denormalizadas com 1 escritor (a função abaixo): `rfb_situacao text`, `rfb_situacao_data date`, `rfb_situacao_lote text` — a UI lê select('*') e mostra o selo sem join.
   - `radar_docs_clientes() RETURNS TABLE(doc text, nome text)` STABLE SECURITY DEFINER, espelho da normalização de radar_recruzar_ja_cliente (não vou tocar a função viva; o CI prova que os dois conjuntos coincidem num seed).
   - `radar_aplicar_situacao(p_lote text, p_agora timestamptz DEFAULT now()) RETURNS jsonb` SECURITY DEFINER, REVOKE PUBLIC/anon/authenticated, GRANT service_role, chamada pela edge no finalize DEPOIS do recruzar:
     (a) UPDATE radar_empresas SET rfb_situacao/data/lote FROM radar_situacao_cadastral WHERE lote=p_lote AND (rfb_situacao_lote IS NULL OR rfb_situacao_lote <= p_lote) — nunca regride para lote mais velho.
     (b) cliente := ja_cliente OR cnpj IN radar_docs_clientes(). LEAD = radar_empresas com NOT cliente AND prospeccao_status NOT IN ('descartado','virou_cliente') AND situação do lote IN ('03','04','08') → INSERT radar_contatos(cnpj,'descartado', nota='RFB: BAIXADA em 12/03/2026 (01 — EXTINCAO POR ENCERRAMENTO LIQUIDACAO VOLUNTARIA)', criado_por = uuid fixo de sistema '00000000-0000-0000-0000-00000000r...'(documentado em COMMENT), status_anterior) + UPDATE prospeccao_status='descartado', descarte_motivo=mesma nota, prospeccao_atualizado_em=p_agora. Re-rodar o mesmo lote: já descartado → 0 linhas (idempotente por estado).
     (c) CLIENTE irregular = cliente AND situação do lote IN ('03','04','08'). NOVO = sem linha anterior em radar_situacao_cadastral com o MESMO (cnpj, situacao) e alertado_em IS NOT NULL (qualquer lote, inclusive o próprio — re-run não repete). Se houver ≥1 novo: 1 INSERT em fornecedor_alerta (empresa 'oben', tipo 'outro', severidade 'atencao', titulo '[Radar] N cliente(s) com baixa/inaptidão no lote YYYY-MM', mensagem = uma linha por cliente "RAZÃO (CNPJ): BAIXADA em dd/mm/aaaa — motivo" + rodapé "de M clientes verificados" (M = clientes distintos com linha de situação neste lote), metadata {origem, lote, cnpjs}); GET DIAGNOSTICS exige 1 linha; depois UPDATE alertado_em=p_agora nas linhas (cnpj NOVO, lote=p_lote). Razão social: COALESCE(radar_empresas.razao_social, nome vindo de radar_docs_clientes()).
     (d) situação 02 ou 01: só (a). Retorno jsonb {lote, leads_descartados, clientes_verificados, clientes_irregulares, clientes_alertados_novos, alerta_id}.
3. Edge radar-ingest (bump VERSAO v1.2): `cnpjs_conhecidos`, `chunk_situacao` (upsert onConflict cnpj,lote; payload NÃO inclui alertado_em → preservado por omissão), finalize chama radar_aplicar_situacao e devolve o jsonb. Erro da RPC propaga (lote vira 'error').
4. UI: selo "Baixado/Inapto/Suspenso pela RFB em dd/mm/aaaa" na linha e na ficha quando rfb_situacao IN ('03','04','08').

Provas: vitest do parser/normalização (scripts/radar/situacao.ts) e dos helpers de rótulo; PG17 db/test-radar-situacao-cadastral.sh com p_agora fixo e sabotagens (lead ativo não descartado; cliente baixado gera 1 alerta e não repete em lote seguinte; situação 02 não faz nada; cliente fora do radar coberto; anon sem EXECUTE); invariantes da edge como texto.

## RÉGUA
- Unidade decisória: (cnpj, lote) observado na RFB; a decisão de produto é (i) tirar lead da fila (prospeccao_status) e (ii) 1 e-mail por lote listando clientes com irregularidade NOVA.

- Como a prova falsifica: sabotar a função (descartar cliente; alertar de novo no lote seguinte; descartar situação 02; ACL aberta) e exigir vermelho no assert declarado após controle verde na mesma invocação.
